# ADR-0040: NVMe

- Status: Accepted
- Date: 2026-10-04
- Depends on: ADR-0021 (PCI and userspace drivers), ADR-0022 (filesystem
  on disk), ADR-0035 (mounts)

## Context

The only disk driver was virtio-blk, which exists only in virtual
machines. Modern PCs and laptops, the Tier 1 targets (ADR-0005), store
their data on NVMe SSDs. Phase 4 lists NVMe first, and booting a real
machine needs it.

NVMe is a public, stable standard (NVM Express Base Specification). Every
controller speaks the same register interface and command set, so one
driver covers the whole class. The PCI class is 01 (mass storage),
subclass 08 (non-volatile memory), interface 02 (NVMe).

## Decision

- **A userspace driver, `nvme`**, built like virtio-blk (ADR-0021).
  - **Authority:**
    - one device capability, taken by class (`grant =
      device-class:010802`, the first NVMe controller);
    - the endpoint it serves;
    - a log.
  - **Protocol:** it serves the block protocol unchanged, so the fs
    service, `disk` and anything else that uses a block service work on it
    as they are.
- **The controller interface:**
  - BAR 0 registers. The controller is reset (`CC.EN = 0`, waiting for
    `CSTS.RDY = 0` within `CAP.TO`), then enabled with:
    - the admin queue (`AQA`, `ASQ`, `ACQ`);
    - 4 KiB pages;
    - 64-byte submission and 16-byte completion entries.
  - **Admin commands:**
    - `IDENTIFY` of the controller, the active namespace list (namespace 1
      on NVMe 1.0 controllers, which lack it) and the namespace;
    - `SET FEATURES` (one queue pair);
    - creation of one I/O completion queue and one I/O submission queue.
  - **Interrupts:** completions raise MSI-X vector 0 on a notification
    (both queues). Without MSI-X the driver polls, with pin interrupts
    masked (`INTMS`).
  - **Completions** are recognised by their phase tag. Doorbells use the
    stride `CAP.DSTRD` gives.
- **Data path:**
  - One command is in flight at a time, as in virtio-blk.
  - Each command moves data between the disk and a 128 KiB bounce buffer
    of contiguous DMA memory. The buffer is described with PRPs: one entry,
    two, or a PRP list prepared once for the whole buffer.
  - A transfer is limited by the buffer and by the controller's maximum
    (`MDTS`).
  - Clients copy through their session buffers, as with virtio-blk: no
    client sees a physical address.
- **Block sizes:**
  - The protocol's sectors are 512 bytes. Namespaces with 512-byte blocks
    map one to one.
  - Larger blocks (up to 4 KiB) are served by whole blocks around each
    request; a write covering part of a block reads the block first
    (`oceans_nvme::next_chunk`).
  - Formats with metadata are refused with a log line.
- **Durability:**
  - With a volatile write cache (`VWC`), the block protocol's `FLUSH` sends
    NVMe `FLUSH`; without one, completed writes are durable.
  - When the service stops, the controller gets a normal shutdown
    (`CC.SHN`).
- **Failures:**
  - A command error is logged with its NVMe meaning and mapped to a block
    status: write protected → read-only; LBA out of range → out of range;
    invalid opcode → unsupported; anything else → I/O error.
  - A command not completed within 30 s, or a controller fatal status,
    resets the controller and brings it up again.
  - A controller that cannot be brought back answers `IoError` and is
    logged.
  - Device-reported sizes and indices are bounds-checked.
- **`libs/nvme` (`oceans-nvme`)** holds everything that is plain data, so
  it is tested on the host:
  - registers and `CAP`;
  - command encoding and completion decoding;
  - identify parsing;
  - PRPs;
  - the sector-to-block translation;
  - ring bookkeeping.
- **In the system:**
  - **Service:** `nvme` provides the endpoint `nvme`.
  - **Filesystem:** a second fs instance, `nvmefs` (`use = nvme as
    block`), keeps an Oceans volume on it: a blank disk is formatted, as
    on the system disk. The system fs shows it as `/nvme` (a mount point,
    ADR-0035).
  - **Logs:** fs instances other than the system's now name themselves in
    their log lines (`fs (nvmefs): `). They get `/bin` only when given
    modules.
  - **Shell:** the shell may use `nvme` (`run disk out use:nvme -- info`).
  - **QEMU:** both `cargo xtask run` and the smoke test attach an NVMe
    controller with a 16 MiB namespace.

## Consequences

- Oceans reads and writes NVMe disks, the storage of current PCs.
  - **Real machines:** the system disk on such a machine is a
    configuration change, `use = nvme as block` for the system fs; nothing
    in the fs changes.
  - **Booting from NVMe** (the boot loader and image on its ESP) is
    firmware work, for when the first real machine is brought up.
- **Speed:** in QEMU, 1 MiB copied from the virtio disk to NVMe takes
  about 0.12 s, including the sync (the USB stick: about 0.2 s).
- **Not done yet:**
  - **Several queues and commands in flight:** one queue pair with one
    command is enough for one filesystem. Real NVMe speed comes from deep
    queues; that needs measurements on real hardware first (§51).
  - **Namespace management, formats with metadata, end-to-end
    protection, TRIM (`DATASET MANAGEMENT`):** not needed by the
    filesystem today.
  - **Hot removal:** NVMe drives are not hot-plugged in the target
    machines.

## Alternatives considered

- **NVMe inside the kernel:** against ADR-0002 and ADR-0021. The driver
  needs nothing a userspace service cannot have through its device
  capability.
- **A shared queue library with virtio:** the two have little in common
  beyond DMA memory (which is shared: `oceans_virtio::Dma`).
- **Several I/O queues from the start:** more complexity without a
  measured need, and one command in flight keeps error handling simple.
- **Refusing namespaces whose blocks are not 512 bytes:** many SSDs ship
  formatted with 4 KiB blocks. Serving them through whole blocks keeps the
  protocol and the filesystem unchanged.

## Checklist (master spec §48)

- **Purpose:** NVMe storage, the first Tier 1 storage controller.
- **Architecture:**
  - the `nvme` service (user/nvme) serves the block protocol;
  - `oceans-nvme` (libs/nvme) holds the data structures;
  - `nvmefs` is an fs instance mounted at `/nvme`.
- **API:**
  - the block protocol (unchanged);
  - the endpoint `nvme`;
  - grant `device-class:010802`.
- **Dependencies:** none (the NVM Express Base Specification).
- **Security:**
  - the driver holds one device capability, its endpoint and a log;
  - clients never see physical addresses;
  - device-reported values are bounds-checked;
  - the driver is isolated: a crash restarts it without affecting the
    kernel.
- **Testing:**
  - **Host unit tests (`oceans-nvme`):**
    - `CAP` decoding and doorbell offsets;
    - command encoding (identify, queue creation, read, write, flush);
    - completion decoding with status meanings;
    - identify parsing, including bad formats and non-ASCII strings;
    - PRP choice;
    - an exhaustive check that every chunk sequence covers a request
      exactly, for 512, 1 024 and 4 096-byte blocks;
    - phase flips.
  - **Smoke (QEMU, release, debug and `-cpu max`):**
    - the controller and namespace are identified;
    - `disk info` through `use:nvme`;
    - the volume is formatted, written (a note and a 1 MiB copy) and read
      back after a reboot;
    - the host mounts the image and compares both files byte for byte.
- **Failure behaviour:**
  - errors are logged and mapped to block statuses;
  - timeouts and fatal status reset the controller;
  - a controller that cannot be reset fails every request;
  - unsupported formats are refused at start with a log line.

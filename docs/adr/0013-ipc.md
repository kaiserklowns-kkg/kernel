# ADR-0013: IPC — endpoints (call/reply) and notifications

- Status: Accepted (kernel-thread level; the syscall interface follows with
  processes)
- Date: 2026-10-03
- Depends on: ADR-0011 (capabilities), ADR-0012 (threads, blocking)
- Inputs: [reference-systems.md](../architecture/reference-systems.md) §1
  (Redox: direct switch, zero-copy, fd passing; the HashMap lookup cost)

## Context

ADR-0002 puts drivers, filesystems and the network stack in userspace
services, so IPC is on every I/O path and is a core Oceans subsystem
(master spec §18). It must carry capabilities (ADR-0011), so authority
flows only through explicit messages. It must fail cleanly when a peer dies,
and its latency must be measured from the start (§51).

## Decision

### Endpoints: synchronous call/reply

- An endpoint is created as **two ends**: `ServerEnd` (receive; needs
  `RECEIVE`) and `ClientEnd` (call; needs `SEND`). Each is a kernel object
  shared by capability, so rights decide who may serve and who may call.
- `call(message) → reply` blocks the caller until the reply arrives.
- `receive() → (request, ReplyToken)` blocks until a call arrives (FIFO
  across callers).
- `ReplyToken::reply(message)` answers exactly one call. Dropping a token
  unanswered fails that call with `NoReply`, so a crashing server never
  strands its callers.
- **Direct switch:** if a server is already waiting in `receive`, `call`
  switches straight to it without going through the ready queue. The reply
  makes the caller runnable, and it runs as soon as the server blocks again.
- **Peer death:** when the last capability to the server end goes, pending
  and future calls fail with `PeerClosed`. When the last client end goes,
  blocked and future receives fail with `PeerClosed` (once queued calls are
  drained).

### Messages

`Message { label: u64, inline data ≤ 256 bytes, ≤ 4 capabilities }`.

- Inline data is copied. Bulk data travels in a **memory object** whose
  capability is attached (zero-copy sharing, with rights such as read-only).
- Attached capabilities **move** to the receiver with the message (the
  sender takes them out of its table with `TRANSFER`). If a call fails with
  `PeerClosed` before delivery, its capabilities are destroyed with the
  message: their intended recipient no longer exists.
- Limits are checked on construction (`MessageTooLarge`,
  `TooManyCapabilities`).

### Notifications

A latched 64-bit signal word. `signal(bits)` ORs bits in and wakes one
waiter, never blocks, and is therefore usable from interrupt handlers (IRQ
delivery to userspace drivers). `wait()` blocks until any bit is set, then
returns and clears them all. Signals sent with nobody waiting are kept.
Rights: `SIGNAL`, `WAIT`. A driver can be given signal-only authority.

### Blocking and correctness

- The scheduler gains `block`, `wake` and `block_and_switch_to` (directed
  switch). Every IPC operation disables interrupts, checks its condition
  and registers the waiting thread under the object's lock, then blocks. On
  one CPU this check-register-block sequence is atomic, so wake-ups cannot
  be lost.
- Each thread has a `blocked` flag. Waking a thread that is not blocked
  **panics** instead of queuing it twice, so state corruption is caught at
  its source.
- Waiting threads are owned by the object they wait on (an `Arc` in the
  waiter list or call slot), which keeps their saved context valid.

### Not yet

- Syscall entry points and per-process tables: they come with processes and
  user mode. The kernel API already takes capabilities, so syscalls only
  translate handles.
- Timeouts on `call`/`receive`/`wait` (needs sleep queue cancellation).
- Asynchronous message queues, if measurement shows synchronous calls plus
  notifications are insufficient.
- SMP: per-CPU wake-up correctness needs the lock hand-off designed with SMP
  scheduling.

## Measurements

Round trip of an empty `call` → `receive` → `reply`, 10 000 iterations,
kernel threads (smoke boot):

| Build | QEMU accel | Cycles / round trip |
|---|---|---|
| debug | TCG (emulation) | ~390 000 |
| release | TCG (emulation) | **~9 000** |

TCG numbers are not hardware numbers; they set a regression baseline.
KVM and real-hardware numbers are to be added to
[benchmarks](../development/benchmarks.md). The obvious next
optimisation is the per-call `Arc<Mutex<Call>>` heap allocation (measure
first, §51).

## Testing

Smoke boot (`oceans.test=smoke`), with all ends reached through capability
tables:
- Inline round trip: the server reverses `"oceans"`.
- Capability transfer: a memory object moves from the client to the server
  table, the server reads it, and the client's handle is gone afterwards.
- A server end does not grant `SEND`.
- Closing the client end ends the server's receive loop with `PeerClosed`,
  after it served exactly the expected number of calls.
- An unanswered call fails with `NoReply`, and calls after the server closes
  fail with `PeerClosed`.
- Notifications: a blocked waiter is woken with the signalled bits, a
  signal-only capability cannot wait, and latched signals merge.
- The 10 000-call benchmark above.

No host unit tests: this logic is all blocking and wake-up interplay with
the real scheduler, which the boot tests exercise. The message limits are
trivial.

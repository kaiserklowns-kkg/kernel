# ADR-0129: Wi-Fi: the Intel Wireless 8260, WPA2-Personal, and one network device

- Status: Accepted
- Date: 2026-10-13
- Depends on: ADR-0023 (the `netdev` protocol), ADR-0123 (`oceans-nic`,
  `grant = device:A,B,...`), ADR-0124 (MSI), ADR-0068 (hardware
  validation), ADR-0053 (directory grants)
- Part of Phase 4 (Hardware) and Phase 10 (Alpha).

## Context

Laptops reach the network by Wi-Fi; most have no Ethernet port in use,
many none at all. The first real machine Oceans is to run on, an HP
ZBook 15u G3, has an Intel Wireless 8260 (`8086:24f3`) beside its I219.

A Wi-Fi chip of this generation is a computer of its own: it runs
Intel's firmware, which the driver loads at every start and then talks
to through host commands. No emulator has one, so whatever is written
is tried first on the real machine, with the log as the only debugger.

The facts come from OpenBSD's `iwm(4)` (ISC licence) and the firmware
file itself, written down first as specs; the code here is new.

## Decision

### The firmware

`iwlwifi-8000C-36.ucode` (2,425,084 bytes, SHA-256
`479931721f5e168d…`), in `firmware/intel/` with Intel's licence: it may
be redistributed as a binary, unchanged, and is not to be reverse
engineered. It is a module of the hardware images, granted to the
driver only (`grant = module:iwlwifi-8000C-36.ucode`), and never runs
on the CPU. QEMU images (the smoke tests) leave it out.

### `oceans-iwm`: what the driver computes, host-tested

- `fw`: the file's TLVs (unknown ones skipped): the INIT and REGULAR
  images, CPU1 and CPU2 sections, paging, PHY SKU, calibration,
  capabilities.
- `reg`, `cmd`, `rx`, `alive`, `nvm`, `paging`: registers, command
  headers and TFDs, packets in a receive buffer, the NVM (address,
  channels, antennas, LAR).
- `mvm`: the commands after ALIVE (auxiliary station, PHY contexts,
  regulatory, scan configuration), the UMAC scan request (v7, 1684
  bytes, sent from its own DMA buffer), received frames (`RX_PHY` +
  `RX_MPDU`).
- `join`: the MAC context, binding, station, session protection, rates
  (`LQ`), what follows association, and `TX_CMD`.

### `iwm`: the driver

1. The chip awake, INIT loaded (ALIVE), the NVM read, calibration.
2. REGULAR loaded, its paged code handed over, the PHY database
   replayed, client mode: the auxiliary station and queue, three PHY
   contexts, "ZZ" when LAR is on, the scan configuration, data queues
   5–8, beacon filtering off.
3. A passive scan of every allowed channel at start; the networks
   logged.
4. Joining: a scan probing for the network; PHY context, rates, MAC
   context, binding, the access point's station, session protection;
   open-system authentication and association (`oceans-wifi`, three
   tries each); then for WPA2 the 4-way handshake over EAPOL
   (`oceans-wpa`'s supplicant).
5. Data: Ethernet frames to and from 802.11 data frames with LLC/SNAP
   (`oceans-wifi`).

Interrupts are polled every 10 ms. Every step is logged; a failure says
where, with the registers that say why.

### WPA2-Personal, encrypted in software

`oceans-wpa`: PBKDF2 PSK, PRF, the PTK, EAPOL-Key frames, the supplicant
(4-way and group handshakes, replay counters), and `Session`: CCMP-128
on every data frame, with its packet number, and replay checks on what
arrives. Nothing is installed in the chip: it carries frames as they
are. A key already in use is never installed again (KRACK); a
retransmitted message 3 is answered and installs nothing.

Only WPA2-Personal with CCMP and open networks are joined; WEP, TKIP,
WPA3 and enterprise networks are listed as not supported.

### One device for the stack

The stack (`net`) has one `netdev` and one address. On a laptop with both
an Ethernet port and Wi-Fi, `iwm` stands between them:

- `use = netdev as wired` (whatever wired driver registered `netdev`
  before it), then `provide = netdev`: the stack talks to iwm.
- Until Wi-Fi joins, the stack's frames pass to the wire and back.
  Once joined, they go by Wi-Fi.
- The wired NIC's address is used on the air too, so the stack's address
  stays the same whichever way frames go.
- Without the chip, init cannot open the device and starts nothing:
  `netdev` stays the wired driver's, as before. If the chip fails to
  come up, iwm still passes frames to the wire.

iwm is started after `fs` (its storage) and before `net`.

### Which network: `/system/wifi`

`grant = storage:/system/wifi`: the files `ssid` and `password`
(none for an open network), which the shell can write:

```
write /system/wifi/ssid MyNetwork
write /system/wifi/password the passphrase
```

The setting decides the security, never the air: with a password only
a WPA2-Personal access point of that name is joined, without one only
an open one. An open look-alike of a WPA2 network (an "evil twin", even
the stronger signal) is refused, and a password never goes to an open
network.

They are read every 2 seconds. A change is followed: a new network is
joined, a removed `ssid` left. A failed join is retried after 20 seconds,
or at once when the setting changes. Control Center's panel uses the
same files (ADR-0130).

## Consequences

- **Laptops with an Intel Wireless 8260** (`8086:24f3`, `24f4`) can join a
  home network, without a cable.
- **Not yet tried on a machine.** The bring-up, scan, join and data
  path are tested only on the host and as specs; the first run is the
  ZBook's, and its log (`diag save`) is what fixes what is wrong.
- **One network at a time, by switching:** if the wire had an address
  from DHCP and Wi-Fi joins another network, the stack keeps the address
  until its lease is renewed. A stack with several interfaces is later
  work.
- **Software CCMP** costs CPU time per frame; the chip's own engine is
  later work.
- **On a USB boot** `/system` is in memory (fs leaves another system's
  disk alone), so the network is set again after each restart; installed,
  it is kept.
- **Later:** other Intel chips (7260, 8265, 9260 need their own
  firmware and a few differences), interrupts instead of polling, power
  save, 802.11n rates, WPA3.

## Alternatives considered

- **The chip's CCMP engine (`ADD_STA_KEY`):** faster, but its packet
  numbers, MIC handling and key state differ between firmware versions;
  software is the same for every chip and is tested on the host.
- **A second interface in the stack:** the right end state, but a
  larger change to `net` (addresses, routes, DHCP per interface) than
  the driver; standing between keeps the stack unchanged.
- **Wi-Fi replacing the wire (iwm registered last, alone):** a laptop
  with an 8260 would lose its Ethernet whenever Wi-Fi is not set.
- **The network in the boot configuration:** not changeable without a
  new image, and the password in the boot partition.

## Checklist (master spec §48)

- Purpose: Wi-Fi for laptops.
- Architecture: a userspace driver with a device capability, a firmware
  module and a storage directory, standing between the stack and the
  wired driver.
- API: no ABI change; the `netdev` protocol as before.
- Dependencies: Intel's firmware (binary, redistributable); RustCrypto's
  `sha1`, `hmac`, `pbkdf2`, `aes`, `ccm`, `aes-kw`.
- Security: the firmware runs on the chip only, with the device's DMA
  as every driver's; frames from the air are untrusted and
  length-checked; keys stay in the driver; the password is in
  `/system/wifi`, readable by what is granted that directory and the
  shell's root.
- Testing: host tests of every computation (the firmware file, command
  layouts, IEEE and RFC vectors, a whole handshake against a simulated
  access point, CCMP both ways); `smoke-hw` boots the profile with the
  new service order; the hardware run is the ZBook's.
- Failure: no chip, no service; a chip that does not come up leaves the
  wire working; a failed join is logged and retried.

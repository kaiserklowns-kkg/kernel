# ADR-0050: Go on Oceans (WebAssembly in a Rust host)

- Status: Accepted
- Date: 2026-10-04
- Depends on: ADR-0001 (language boundaries), ADR-0014 (processes),
  ADR-0020 (handle directories), ADR-0025 (boot archive)
- Starts Phase 6

## Context

The master spec puts Go above the Rust system: system services and the
AI runtime (§5, §8). ADR-0001 adds that Go talks to the system only
through the Oceans System API over IPC. Phase 6 begins by making Go run
on Oceans at all.

**Native Go would mean a new `GOOS` port:**
- the Go runtime assumes threads, futexes, signals and `mmap`, and
  Oceans has one thread per process (ADR-0014) and no POSIX layer;
- the port would be a fork of the Go toolchain to keep in step with
  every release;
- it would not fit what the spec asks of Go here: a high-level service
  language, behind an explicit API.

**Go has a supported WebAssembly target:**
- `GOOS=wasip1 GOARCH=wasm`, in the standard toolchain since Go 1.21;
- WebAssembly modules can only call what their host gives them, so the
  host decides exactly which System API exists for Go code, with every
  pointer checked;
- `//go:wasmimport` imports host functions directly.

## Decision

### The Go host

**`gohost`** (user/gohost) is an Oceans process that runs one Go program
built for wasip1.

- **Its authority** is the process's, granted as usual (init, or Core
  for packages); the module gets nothing more.
- **The program** is the first boot module in its directory
  (`grant = module:NAME.wasm`).
- **The interpreter is wasmi 2.0:**
  - `no_std`, MIT/Apache-2.0, a dependency kept under its license;
  - floating point in software (`libm`), since Oceans user code must not
    use SIMD state;
  - **loop dispatch** (`portable-dispatch`). Without it, wasmi dispatches
    by tail calls, and on a compiler that does not guarantee them every
    executed instruction grew the native stack; it reached 11.5 MiB for a
    small program. With loop dispatch the measured peak is 11 KiB.
- **The stack:** the interpreter runs on a 1 MiB stack of its own,
  through the new `oceans_rt::with_stack` (a memory object and a small
  assembly trampoline). That leaves headroom over the process's 64 KiB.
- **Memory:** the module's linear memory is one large, growing
  allocation. The process heap now serves blocks over its 4 MiB maximum
  directly from memory objects, each at the start of a 1 GiB window of a
  separate region. **Growing one maps another object right after it, in
  place, without copying** (`realloc`).

### The System API binding

Module `oceans` of the host, wrapped by Go package `go/oceans`.

**Operations:**

| Group | Calls |
|---|---|
| Directory | `handle_find` (directory lookup), `args` |
| Log | `debug_write` |
| Handles | `close`, `duplicate` |
| IPC | `ipc_call`, `ipc_receive`, `ipc_reply`, `endpoint_mint` |
| Events | `notification_create`, `endpoint_bind`, `timer_set` |
| Data | `publish_text`, `system_info` |

**Rules:**
- **Pointers** are offsets into the module's memory. **The host checks
  every range** and copies in and out. The module never sees host memory
  or physical addresses.
- **Handles** are the process's own. The module can use only what the
  process holds, as any Oceans program.
- **Limits:** inline messages (256 bytes, 4 handles), as for every
  process. Shared buffers are not available to modules.
- **The API is generated by hand for now.** Generated bindings from a
  protocol description (ADR-0001) come once more protocols are used from
  Go.

### WASI preview 1, the subset the Go runtime uses

| Call | Behaviour |
|---|---|
| `fd_write` to 1 and 2 | the console if granted, otherwise the log a line at a time |
| `args_*` | the program's name and arguments |
| `environ_*` | empty |
| `clock_time_get`, `clock_res_get` | realtime and monotonic clocks |
| `random_get` | kernel entropy |
| `poll_oneoff` | clock subscriptions, which is how Go sleeps |
| `sched_yield`, `proc_exit` | as named |
| `fd_fdstat_*`, `fd_close` | for the standard descriptors |

There are no files or sockets through WASI: on Oceans those are services
reached over IPC. Their WASI calls fail (`EBADF`, `ENOTSUP`).

### The Go module and tooling

- **The Go module** lives at `go/` (module
  `github.com/kaiserklowns-kkg/kernel/go`).
- **`cargo xtask` builds the Go programs:**
  - into the boot archive (`GO_PROGRAMS`), with Go caches under `build/`;
  - Go 1.26 or newer is now a build requirement (`OCEANS_GO` to point at
    one).
- **`cargo xtask check`** runs `gofmt -l`, `go vet` (host and wasip1)
  and `go test`.
- **CI** installs Go.

## Consequences

- Go runs on Oceans with the standard toolchain: goroutines, channels,
  maps, `fmt`, `time` and the GC all work. **What Go can do is exactly
  the host functions plus what the process was granted.** That is the
  sandbox ADR-0007 wants for the AI runtime, and it is the same for any
  Go service.
- **Cost:**
  - modules are a few MB (gohello: 2.7 MB);
  - interpretation is slower than native code. It is fine for services
    that mostly wait for IPC and the network; measure before moving
    anything hot (§51);
  - a JIT is not an option: Oceans forbids writable and executable
    memory (W^X).
- **Not yet:**
  - Go programs installed as packages (Core runs native programs only):
    they come with a package `kind`/runtime field;
  - shared buffers for bulk data;
  - generated bindings.

## Alternatives considered

- **A native `GOOS=oceans` port:** months of work in a fork of the Go
  runtime, which would need threads in the kernel first. Possible later,
  if measurements demand it. The binding API stays the same either way.
- **TinyGo with a custom target:** no goroutine preemption, a partial
  standard library, and another toolchain to install. The standard Go
  toolchain and wasip1 are supported upstream.
- **Running Go on the host machine and talking to it over the network:**
  then it is not an Oceans service, and it has none of the capability
  sandbox.

## Checklist (master spec §48)

- **Purpose:** Go programs as Oceans processes.
- **Architecture:**
  - `gohost` (wasmi, WASI subset, `oceans` host functions);
  - `go/oceans` binding;
  - `oceans_rt::with_stack`;
  - huge heap blocks.
- **API:**
  - the `oceans` host module (above);
  - Go package `oceans` (`Find`, `Call`, `Receive`, `Reply`, `Mint`,
    `DebugWrite`, …);
  - `grant = module:NAME.wasm`.
- **Dependencies:** wasmi 2.0 (MIT/Apache-2.0); Go 1.26 to build.
- **Security:**
  - modules reach only host functions;
  - every pointer range is checked;
  - handles are the process's own (no new authority);
  - no W+X memory (interpreted).
- **Testing:**
  - **Smoke, every boot:** service `gohello` (Go, through `gohost`):
    - prints its Go version;
    - runs goroutines over channels;
    - sleeps (`poll_oneoff`);
    - calls the echo service through the binding and checks the answer;
    - writes to the log, and must exit 0 (init checks).
  - **Host:** `go vet` for both targets; `gofmt`.
- **Failure behaviour:**
  - a module that does not validate or instantiate is logged, with exit
    code 4;
  - a trap is logged, with exit 5;
  - `proc_exit` codes are passed through;
  - Go's own fatal errors reach the log through `fd_write`.

# ADR-0032: USB: an xHCI driver and boot keyboards

- Status: Accepted
- Date: 2026-10-03
- Depends on: ADR-0021 (device capabilities), ADR-0029 (console input), ADR-0016 (init)

## Context

Most machines have no PS/2 port: keyboards, storage and network
adapters arrive over USB. USB host controllers since USB 3 share one
standard interface, xHCI (PCI class `0c 03 30`), so a single driver
covers them all. Like the other drivers (ADR-0021), it must run in user
space with only the authority it needs.

Two pieces of authority were missing:

- **Opening a device by class.** Device grants named a vendor and device
  ID. That suits virtio, but not a standard interface implemented by
  many vendors.
- **Feeding the console's input.** A keyboard driver must type into the
  console without being able to read what others type or print to the
  screen.

## Decision

- **ABI 11:**
  - `DEVICE_OPEN` accepts class selectors:
    `CLASS_SELECTOR | class << 16 | subclass << 8 | prog_if`. The kernel
    opens the `index`th function of that class, exclusively, as before.
  - System call 40 `CONSOLE_INPUT` appends bytes to the console's input
    as if typed. It needs the new `MANAGE` right on the console.
- **init grants:**
  - `device-class:CCSSPP` opens the first device of that class.
  - `console-input` is a console capability with only `MANAGE` (and
    `TRANSFER`, needed to hand it over). With it, the holder can type but
    can neither read nor print.
  - The `usb` service gets `device-class:0c0330`, `console-input`,
    `provide = usb` and a log.
- **`libs/usb` (`oceans-usb`, host-tested, no allocation).** It holds
  everything that is pure protocol:
  - **Descriptors:** device, configuration, interface, endpoint and
    string. They are parsed as untrusted input: lengths are checked, and
    a malformed item ends the walk.
  - **Requests:** setup packets for `GET_DESCRIPTOR`,
    `SET_CONFIGURATION`, HID `SET_PROTOCOL` and `SET_IDLE`.
  - **The HID boot keyboard:** reports become the same bytes the PS/2
    keyboard sends: ASCII with Shift, Caps Lock and Ctrl, the keypad,
    Enter as CR and Backspace as DEL. A held key is reported once, and
    roll-over reports are ignored.
  - **xHCI structures:**
    - register offsets and bits;
    - TRB encoding and event decoding;
    - the producer and consumer cycle-bit discipline, with link TRBs;
    - input contexts;
    - interval conversion;
    - a `PORTSC` write helper that never acknowledges a change or
      disables a port by accident.
  - The `usb` endpoint protocol (`LIST`, 40-byte records).
- **The `xhci` driver** (a user service):
  - **Controller bring-up:** legacy handoff from the firmware, halt,
    reset, a 4 KiB page check, the device context array, scratchpad
    buffers, a one-page command ring, and one event ring segment.
    Interrupts use MSI-X through a notification bound to the endpoint,
    with a 10 ms polling fallback.
  - All DMA memory comes from one device-owned pool, one page per
    structure. A port's pages are reused when it is replugged.
  - **Enumeration** on every root port at start, and on port status
    change events (hot plug):
    1. reset USB 2 ports;
    2. enable a slot;
    3. address the device;
    4. read 8 bytes of its descriptor for endpoint 0's packet size, and
       evaluate the context if it differs;
    5. read the full device descriptor, the product string and the first
       configuration.
    - On removal, the slot is disabled.
  - **Boot keyboards:**
    - select the configuration;
    - select the boot protocol, and set idle (a stall is tolerated);
    - configure the interrupt IN endpoint;
    - keep four 8-byte reports queued. A report's buffer is chosen by its
      TRB's index, so a completion finds its data without bookkeeping.
    - New keys go to the console through `CONSOLE_INPUT`.
  - Mice, storage and hubs are recognised and listed but not driven.
- **`lsusb`** (`run lsusb out use:usb`) lists port, IDs, product, speed,
  and what the driver does with each device.

## Consequences

- Keyboards on USB-only machines work, with no kernel changes per device
  class. The kernel still knows nothing about USB.
- A compromised or buggy USB driver can inject keystrokes, but cannot
  read console input, print, or touch other devices. That is no worse
  than a physical keyboard.
- **No hub support yet:** only devices on root ports are seen. Hubs need
  route strings and a hub class driver.
- **No other class drivers yet:** mass storage, network adapters and
  mice are listed only. The control-transfer and ring code is ready for
  them.
- **No key repeat:** boot keyboards do not repeat in hardware, so a
  held key types once (as on the PS/2 path).
- **One interrupter, one event ring segment, one controller:** enough
  for keyboards; throughput classes may want more.

## Alternatives considered

- **xHCI in the kernel:** a large, DMA-heavy driver in the trusted
  computing base, and against ADR-0021.
- **A UHCI/EHCI driver first:** legacy controllers that new machines do
  not have. QEMU, and hardware since about 2010, provide xHCI.
- **Keyboard input through a terminal service:** the right shape once
  there are several consoles. For one system console, a narrowly scoped
  kernel right is simpler and cannot leak input.
- **Matching xHCI by vendor and device ID:** every controller model
  would need its own grant line.

## Checklist (master spec §48)

- **Purpose:** USB keyboards on real hardware; the base for further USB
  classes.
- **Architecture:** a user-space xHCI service; protocol logic in a
  host-tested library; two narrowly scoped kernel additions (class
  selectors and `CONSOLE_INPUT`).
- **API:**
  - `CONSOLE_INPUT` (40), `class_selector`,
    `oceans_rt::{console_input, device_open_class}`;
  - grants `device-class:CCSSPP` and `console-input`;
  - endpoint `usb` (`LIST`); `lsusb`.
- **Dependencies:** none new (`oceans-virtio`'s DMA helper is reused).
- **Security:**
  - the driver holds one device and a type-only console right;
  - descriptors are parsed defensively;
  - DMA stays in the driver's own pool;
  - register offsets reported by the controller are checked against
    BAR 0.
- **Testing:**
  - 18 host tests: descriptors (including hostile ones), setup packets,
    keyboard reports (shift, caps, ctrl, keypad, roll-over, held keys),
    TRB and event encoding, ring wrap with cycle toggling, input
    contexts, port writes, intervals and records.
  - The smoke test boots with `qemu-xhci` and `usb-kbd` and runs
    `lsusb` with and without its grant. It types a command through the
    USB keyboard via QEMU's monitor, and runs it in the shell; a run
    without `console-input` confirmed those keys came through USB, not
    PS/2. It also hot-plugs a USB mouse, checks that `lsusb` lists it,
    removes it, and checks that it is gone.
- **Failure behaviour:**
  - if the controller cannot start, the driver exits and init's restart
    policy applies;
  - a device that fails enumeration gets its slot disabled and is
    reported in the log;
  - other devices are unaffected.

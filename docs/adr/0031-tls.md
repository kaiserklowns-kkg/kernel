# ADR-0031: TLS and wall-clock time

- Status: Accepted
- Date: 2026-10-03
- Depends on: ADR-0026 (entropy), ADR-0028 (HTTP client), ADR-0030 (shared buffers)

## Context

`fetch` speaks only plain HTTP (ADR-0028), but almost every server now
requires HTTPS. A TLS client needs four things:

- randomness for key exchange (ADR-0026 provides it);
- cryptography for the handshake and for records;
- trust anchors to check certificates against;
- the current date, to check certificate validity periods.

The kernel only knew the time since boot.

Two constraints shape the design:

- Oceans does not save SSE/AVX state across context switches, and
  `CR4.OSFXSR` is clear. Any SIMD instruction in user code would fault,
  or would corrupt another process's registers. User code must therefore
  stay scalar.
- A TLS stack is a large, sharp piece of security code. Writing our own
  would be the riskiest choice.

## Decision

- **Wall-clock time (ABI 10):**
  - At boot the kernel reads the CMOS real-time clock once. It waits out
    an update, takes two readings that agree, and handles BCD or binary
    values and 12- or 24-hour mode. Century register `0x32`, with 20xx
    assumed if unusable. The clock is read as UTC.
  - Afterwards the wall clock is the boot time plus the monotonic tick
    clock. It never jumps and never goes backwards while running.
  - System call 39 `TIME` returns Unix milliseconds, or `NotFound` if
    there is no usable clock. Like `RANDOM`, it needs no capability,
    because the time grants no authority.
  - The calendar arithmetic (`days_from_civil`) is self-tested against
    known dates. A new `date` utility prints the time.
- **TLS: rustls 0.23 in `no_std` mode (`libs/tls`, `oceans-tls`):**
  - The crate uses rustls's unbuffered connection API and our own crypto
    provider, built from RustCrypto and dalek crates:
    - Suites: TLS 1.3 and 1.2 with ChaCha20-Poly1305 and
      AES-128/256-GCM. ChaCha20 comes first: in software it is several
      times faster than AES.
    - Key exchange: X25519, P-256 and P-384. NIST points must be
      uncompressed. A non-contributory X25519 result is refused.
    - Certificates and handshake signatures: ECDSA (P-256, P-384 with
      SHA-256/384), Ed25519 (strict verification), RSA PKCS#1 v1.5 and
      RSA-PSS with SHA-256/384/512, for 2048- to 4096-bit keys.
    - Hashes: SHA-256/384. HMAC, HKDF and the TLS 1.2 PRF are built on
      them.
  - Trust anchors are Mozilla's roots (`webpki-roots`), compiled in.
  - `Client<T: Transport>` is a blocking client over any byte stream. It
    drives the rustls state machine with growable buffers. Handshake
    messages are capped at 256 KiB.
  - A connection that ends without `close_notify` is reported as
    `Truncated`, never as a clean end of data.
  - Server-side signing (P-256) exists only behind the `server` feature,
    for tests and tools.
- **Software crypto only:**
  - User programs are built with `aes_force_soft`, `polyval_force_soft`,
    `chacha20_force_soft`, `poly1305_force_soft` and the serial
    curve25519 backend, with `sha2`'s `force-soft` feature.
  - Without these, runtime CPU detection would pick AES-NI, SHA-NI or
    AVX2 paths.
  - The software AES is bitsliced, so it is constant-time.
  - User dependencies are optimised even in debug builds
    (`opt-level = 2`).
  - User debug info is stripped in debug builds too. The TLS stack would
    otherwise add about 30 MiB to the boot archive.
- **`fetch https://…`:**
  - Randomness comes from `RANDOM` and time from `TIME`.
  - Server names may be DNS names or IP addresses.
  - `--ca PATH` adds the certificates in a file (PEM or DER) to the
    roots.
  - Redirects keep the scheme. A redirect from `https` to `http` is
    refused (`HttpError::Downgrade`).
  - When saving, `fetch` reports the negotiated protocol and suite.

## Consequences

- **Real servers work:** `fetch` downloads from example.com, Google,
  GitHub, Wikipedia, Let's Encrypt and Cloudflare (tested by hand) over
  TLS 1.3.
- **Throughput:** 256 KiB over TLS from OpenSSL takes about 250 ms in a
  release build.
- **Size:** `fetch` grows to about 1.3 MB in release, mostly the root
  store and RSA.
- **Trust anchors are fixed at build time.** Updating them means a new
  build. A system trust store (a file, or a service) can replace the
  compiled-in roots later without changing the API.
- **No revocation checking** (CRL or OCSP). Short-lived certificates make
  this tolerable for now.
- **The RTC is trusted.** A wrong clock makes valid certificates fail
  (`NotValidYet` or `Expired`) rather than making invalid ones pass,
  except for expired certificates if the clock is set back. Network time
  (NTP) is future work.
- **The `rsa` crate** carries RUSTSEC-2023-0071, a timing side channel in
  decryption and signing with private keys. We only verify with public
  keys, which that advisory does not affect.
- **Licences:**
  - rustls: Apache-2.0, MIT or ISC; rustls-webpki: ISC.
  - RustCrypto: MIT or Apache-2.0.
  - dalek: BSD-3-Clause.
  - `webpki-roots`: CDLA-Permissive-2.0.
  - All are compatible with distribution. The project licence is still
    open (ADR-0001).
- **Init limit:** init's per-service grant limit rose from 16 to 24 (the
  kernel allows 32 initial handles), because the shell now holds 17.

## Alternatives considered

- **Our own TLS implementation:** a large attack surface written from
  scratch. rustls is memory-safe, audited and widely deployed.
- **embedded-tls:** TLS 1.3 only, and its certificate verification is
  experimental. Many servers still negotiate TLS 1.2.
- **ring or aws-lc-rs as the provider:**
  - They need C and assembly toolchains for a bare-metal target, which
    are not supported here.
  - Their SIMD code would need kernel FPU state saving first.
- **The `rustls-rustcrypto` provider crate:** alpha quality, and it
  trails rustls releases. Our provider is about 600 lines we fully
  control.
- **Enabling SSE/AVX in user space now:** this needs per-thread FPU state
  (xsave/xrstor) on every switch. It is worthwhile later for speed, but
  not needed for correctness.

## Checklist (master spec §48)

- **Purpose:** HTTPS for `fetch`, plus wall-clock time for the system.
- **Architecture:** a kernel RTC read at boot; `TIME` (ABI 10); rustls
  over a pure-Rust provider in a host-tested library; programs supply
  randomness, time and transport.
- **API:**
  - `TIME`, `oceans_rt::unix_time_ms`;
  - `oceans_tls::{provider, web_roots, client_config, parse_certificates, Client, Transport}`;
  - `Url::secure`, `HttpError::Downgrade`;
  - `fetch [--ca PATH] URL [PATH]`; `date`.
- **Dependencies:** rustls, webpki-roots, RustCrypto (aes-gcm,
  chacha20poly1305, sha2, hmac, p256, p384, rsa), x25519-dalek,
  ed25519-dalek.
- **Security:**
  - certificates are fully validated: chain, name or IP, validity
    period, and key usage;
  - no downgrade on redirects;
  - truncation is detected;
  - no SIMD in user code;
  - `TIME` and `RANDOM` need no capability.
- **Testing:**
  - Host tests (`oceans-tls`): real handshakes against a rustls server
    for every TLS 1.3 suite with every group, every TLS 1.2 ECDSA suite,
    and certificates of every signature algorithm (ECDSA, RSA, PSS,
    Ed25519). Also a 1 MB body, and refusals for an unknown issuer, a
    wrong name, expired and not-yet-valid certificates, and a missing
    `close_notify`.
  - The kernel self-tests its calendar arithmetic.
  - The smoke test runs `date`, then fetches the test CA over HTTP. It
    checks that `https` fails with `UnknownIssuer` without `--ca`, then
    with `--ca` fetches text and a 256 KiB file from OpenSSL's
    `s_server`. The file is verified byte for byte on the host.
- **Failure behaviour:**
  - every TLS error is reported with rustls's description, and nothing
    is saved as complete;
  - with no RTC, `TIME` fails and so does certificate validation.
